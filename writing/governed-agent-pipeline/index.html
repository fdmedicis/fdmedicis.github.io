I say two words. An AI changes my website. Another AI checks it first.

A voice note becomes a pull request, a second model reviews it, and low-risk changes deploy themselves. The interesting part is not the speed — it is what had to be true for it to be safe.

30 October 2026

I sent a voice note to a private Discord channel: “photo me”. Two minutes and eleven seconds later, the photo on this site had changed — and no human had touched the code, the pull request, or the merge button.

That is the visible part. Everything below is what had to be in place for it to be safe.

Why I built it

The shift with AI is not “AI writes code”. It is that agents now do multi-step work with real tools, and the human job moves from doing to orchestrating and governing. I wanted hands-on practice in the rare part of that skill: designing systems where an agent can act on its own — and where it cannot, by construction.

So I set a deliberately small, deliberately public target: a spoken command that changes my live landing page, going through the whole pipeline — understand, change, independent review, deploy — with low-risk changes shipping by themselves and high-risk ones waiting for me. Smallest possible blast radius, whole pipeline.

What happens when I speak

  1. Discord #lab — I send a voice note, or type. The bot listens in that channel only, and only to me.
  2. Transcription — Whisper turns it into text, with an English pass, because I mix Spanish and English.
  3. Intent, not code — the text can only select an entry from a fixed table. Nothing I say ever becomes code, and a sentence containing a negation (“don’t change…”) is refused rather than guessed at.
  4. It asks first — it tells me what it understood and waits for a reaction within 60 seconds. No confirmation, nothing happens.
  5. It opens a pull request — as itself. The agent acts through its own GitHub App identity, not my account. That identity can open pull requests, but it cannot change CI workflows and cannot approve its own work.
  6. A second AI reviews it. My cross-model review gate sends the change — including the image itself — to a different model, and gets back a binary verdict, a risk tier and reasons, posted on the pull request.
  7. Asymmetric authority. VALID and low risk, and a required approval check passes on its own and the pull request merges itself. High risk — workflows, security files, how the site is served — and that check fails until I approve that exact commit.
  8. Deploy and verify. GitHub Pages publishes, and the bot confirms the live site serves the new file byte for byte before reporting back.

The moment it said no

The first real run failed, and it is my favourite part of the whole thing.

My first design changed one line of HTML to point at a different photo already in the repository. The gate answered NOT VALID: the referenced image “is unavailable to inspect, so its suitability cannot be verified”. A reviewer only sees what a pull request changes, and I was asking it to approve a picture it had never been shown.

It was right. A one-line path change looks harmless, and it is exactly the shape of change that could put anything on a public page. So I changed the design rather than the gate: the page now always displays one fixed file, and a swap replaces that file’s contents. The pull request therefore carries the picture itself, and the second model looks at it before anything can merge. The next run went through.

A gate is only worth having if it can stop you — and only worth trusting if, when it does, you fix the cause instead of routing around it.

Governance, built in rather than bolted on

  • Cross-model, not self-review. A model reviewing its own work is an echo with the same blind spots. The gate is a separate, public project, and I tested it against deliberately bad changes before trusting it: 13 out of 13 caught with each of three providers, with the false positives traced and fixed.
  • No reviewer shopping. If a reviewer returns a verdict, that is the verdict. It falls back to another model only when the first gives no answer at all — an outage or a quota — never because I did not like the result.
  • Secrets never reach a model. A deterministic secret scan runs before any AI sees the diff.
  • Its own identity, least privilege. The agent has only the permissions it needs. It cannot edit workflows, and infrastructure changes are owner-only.
  • The rules live with the code. Each repository declares what counts as high risk in its own instructions file, and the gate and the merge rules enforce that in code rather than in good intentions.
  • Only images I have the right to publish — which is why the alternates are a public-domain fox, owl and wolf. Rights are part of governance too.

What it cost

Cents per change: one transcription, one small language pass, one review. No servers — the bot runs on a machine I already have on, and GitHub Pages is free.

What is next

Each step widens the blast radius and needs more governance in step: a photo swap, then content edits, then a new component, then a project from zero. Next is letting it find an image rather than choose from a vetted set — public domain only, shown to me first, credited automatically — with the gate looking at every picture before it goes anywhere near the page.

The gate is open source: github.com/fdmedicis/cross-model-review-gate.
